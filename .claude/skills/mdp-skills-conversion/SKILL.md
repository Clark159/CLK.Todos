# 通用 SKILL 轉換規範

這份 Skill 不綁定任何特定規則來源、不限任何技術領域：不管使用者要
轉換的規則來源是什麼檔案、寫的是哪個領域的規則，當使用者要求「把某份
規則文件轉換／翻譯成 SKILL.md」時，都依下列規則，在「規則來源所在
資料夾」整份重新生成一份 `SKILL.md`（不做局部修補、不留舊內容）。生成
後依「驗證」一節逐條比對，發現任何不吻合都回頭調整本 Skill（這份
`mdp-skills-conversion/SKILL.md`）的轉換規則，再依調整後的規則重新
生成整份目標 `SKILL.md`，不直接手改目標 `SKILL.md` 本身；目標
`SKILL.md` 永遠是依本 Skill 規則重新生成的產物，不單獨維護。改到逐條
吻合為止，轉換才算完成。

以下用 `{來源檔案}` 代稱使用者指定的規則來源文件（若使用者呼叫本
Skill 時有帶參數，參數即為 `{來源檔案}` 路徑；沒有帶參數就詢問使用者
要轉換哪一份規則文件），用「目標 `SKILL.md`」代稱本次轉換要生成的產物
（放在 `{來源檔案}` 所在資料夾），跟本 Skill 自己的 `SKILL.md`（也就是
你正在讀的這份檔案）是兩份不同的檔案，不要混淆。

## 使用方式

`{來源檔案}` 的規則本文有變動（新增／修改／刪除某條規則）之後，目標
`SKILL.md` 就跟著過期，要整份重新生成。呼叫本 Skill 時指名 `{來源檔案}`
即可，不用重複規則內容，例如：「用 mdp-skills-conversion 把
`architecture.md` 轉換成 SKILL.md」。

## 轉換前：分析來源文件結構

`{來源檔案}` 不保證具備固定的段落結構（不保證一定分「規則／範例／
說明」），轉換前要先讀過全文，判斷每個段落屬於哪一種性質，再套用後面
的轉換規則：

- **規則本文**：規範性敘述，內容是「要求」「禁止」「必須」「命名規
  則」「順序」「格式」這類 AI 執行時要精確遵守的規定。
- **範例／說明**：解釋規則背後原因、舉具體案例佐證、比較寫法好壞的
  敘述；目的是幫助人類理解，不是給 AI 執行時逐條核對的規定本身。
- 如果 `{來源檔案}` 本身已經用標題明確區分這兩類段落（例如「規則」
  「範例」「說明」小節），直接依標題判斷即可。
- 如果 `{來源檔案}` 沒有用標題區分，逐段落／逐句判斷：陳述「應該
  怎麼做」「命名為何」「順序為何」的句子歸類為規則本文；陳述「為什麼
  這樣做」「舉例來說」「比較起來」的句子歸類為範例／說明。判斷不確定
  時，寧可保守歸類為範例／說明（不搬進目標 `SKILL.md`），也不要把推理
  過程誤搬成規則本身。
- 這一步的分析結果不用寫進目標 `SKILL.md`，只是轉換過程的中間判斷
  依據；必要時可以在回報轉換結果時說明對 `{來源檔案}` 做了哪些段落性質
  的判斷。

## 規則

- 只轉換「規則本文」；「範例／說明」性質的段落一律不搬過去，目標
  `SKILL.md` 不放具體程式碼範例、不放舉例說明、不放比較好壞的推理
  文字。
- 規則本文逐條照搬，不得漏掉任何一條；也不得把範例／說明段落的推理
  文字接到規則 bullet 後面（例如用「——」或括號補一句原因），即使只是
  改寫成一句話。規則本身要單獨站得住腳，推理／原因留在 `{來源檔案}`
  的範例／說明段落即可，需要時人類或 AI 直接回來看那裡。
- 「逐條照搬」要做到字句層級，不是只核對 bullet 數量對不對：同一條
  bullet 裡的括號例子、附帶子句（語氣強調或舉例）都要完整保留，不能
  因為看起來像次要資訊、可有可無，就在轉換時省略或改寫成精簡版。轉換
  完成後要逐條比對兩份文件的規則文字，不是只看章節數或 bullet 數量相同
  就視為吻合。
- 如果 `{來源檔案}` 本身有定義佔位符凡例（例如用 `{Domain}`／`{Entity}`
  代稱專案／類別名稱，開頭有說明這是佔位符），規則本文與行內程式碼片段
  一律照抄凡例、延用同一套佔位符，不出現具體專案／類別名稱；這條也涵蓋
  行內程式碼片段裡綁定名稱的變數（不是只看 PascalCase 的類別／方法
  名稱）。若轉換時發現規則本文混進具體名稱，代表 `{來源檔案}` 本文自己
  違反了它定義的凡例，屬於正本的缺陷：先回頭修正 `{來源檔案}` 本文（把
  具體名稱改寫成凡例定義的佔位符，不是刪掉那段規則），修好後再照修正後
  的文字轉換，不要在生成目標 `SKILL.md` 時單方面把具體名稱代換成佔位
  符、放著 `{來源檔案}` 本文的缺陷不動。
- 如果 `{來源檔案}` 沒有定義佔位符凡例（規則本身就是用具體名稱、具體
  技術、具體慣例撰寫，沒有要泛用到別的專案／領域），就照原文的具體名稱
  轉換，不要臆測套用一套佔位符規則；是否使用佔位符，依 `{來源檔案}`
  本身有沒有這個凡例決定，不是本 Skill 自己規定要或不要。
- 程式碼區塊能不能保留，看它在 `{來源檔案}` 原本放在規則本文段落還是
  範例／說明段落，不是看它改寫後像不像樣板：只有原文放在規則本文段落
  裡的程式碼區塊（例如規範方法簽章的樣板）可以保留；原文放在範例／
  說明段落的程式碼區塊一律移除，即使套用佔位符後看起來也像樣板，也不
  能保留。
- 目標 `SKILL.md` 全文（含 frontmatter）不得出現對 `{來源檔案}` 或本
  Skill 的檔案參照、連結或提及；目標 `SKILL.md` 要能被獨立閱讀、獨立
  套用。
- 章節標題與編號跟 `{來源檔案}` 本文逐節一一對應，`{來源檔案}` 新增／
  刪除／調整章節時，目標 `SKILL.md` 的章節結構要同步跟著變，方便逐節
  核對轉換有沒有漏掉規則。
- frontmatter 的 `name` 依規則來源所在的 skill 資料夾名稱決定，不寫死
  成任何特定名稱、轉換不同來源時不強制沿用舊值；`description` 依「這份
  規範管什麼、什麼時候要讀」重寫，不綁定任何專案名稱、不提
  `{來源檔案}`。
- frontmatter 欄位只能用 Claude Code 目前版本支援的欄位：`name`、
  `description`、`argument-hint`、`disable-model-invocation`、
  `user-invocable`、`compatibility`、`license`、`metadata`；不得加入
  `allowed-tools` 等不支援的欄位。
- frontmatter 的 `metadata` 底下加一個時間戳記欄位（例如
  `metadata.generated`），記錄「這次重新生成」的日期時間；只能出現這一
  處，不要在 frontmatter 之外的正文裡重複記錄。
- `metadata.generated` 只有在目標 `SKILL.md` 本次重新生成的內容跟現有
  檔案不同時才更新成本次時間；如果比對後發現本次生成的內容（時間戳記
  以外的部分）跟現有目標 `SKILL.md` 完全一樣，就保留現有的
  `metadata.generated` 值不動，不要單純因為「重新跑了一次轉換」就覆寫
  成新時間；也不用去查詢或保留比現有值更早的原始建立時間。
- 目標 `SKILL.md` 除了逐節對應的規則本文之外，還要有「使用時機」「自我
  檢查清單（寫完之後逐條核對）」兩個給 AI 執行用的段落；這兩段不是
  逐節對應 `{來源檔案}` 的某一節，是彙整全文規則 bullet 展開／改寫出來
  的可執行版內容，`{來源檔案}` 本文沒有同名段落也要生成，不能因為「找不到
  對應段落」就略過。若 `{來源檔案}` 的規則內容環繞著某個明確的執行流程
  （例如新增一個特定種類的項目、走一次特定流程），額外加一段對應該流程
  的「執行清單」，彙整跟該流程有關、分散在好幾節的規則，列成步驟清單；
  規則內容不圍繞任何特定執行流程時，不用勉強生出這一段。清單裡的路徑與
  命名，若 `{來源檔案}` 有佔位符凡例就延用佔位符，沒有就延用原文具體
  名稱。
- 「使用時機」段落：依整份規範管什麼、什麼時候該讀，概述一段話，供
  AI 判斷何時要套用這份規範。
- 「自我檢查清單」段落缺漏視同轉換不完整。清單顆粒度要跟到每一條規則
  bullet，不是每個章節縮成一條：一個章節如果有好幾條規則，能個別檢查、
  個別會不會漏做的，就拆成好幾條檢查項目分別列出，不要為了清單簡短，把
  好幾條不同規則揉成一條、讓其中任何一條被漏做時清單看起來還是打勾過得
  去；只有規則之間本來就是同一件事的不同面向（例如同一條命名鏈貫穿好
  幾節、每節只是那條鏈的一個環節）才合併成一條。

## 驗證（生成後必做，收斂前不算完成）

- 生成目標 `SKILL.md` 後，要拿 `{來源檔案}` 每一節的規則本文逐條跟目標
  `SKILL.md` 對應章節比對，不是只核對章節數或 bullet 數量相同；比對時
  發現任何不吻合（漏掉的 bullet、漏掉的括號例子或子句、多出來的說明
  文字或具體名稱、佔位符套用錯誤），就依照上面各條規則調整本 Skill
  （這份 `mdp-skills-conversion/SKILL.md`），再依調整後的規則重新生成
  整份目標 `SKILL.md`，改完再重新比對一次，直到逐條吻合為止，才算完成
  這次轉換。
- 「使用時機」「自我檢查清單」（以及視情況生成的「執行清單」）這些段落
  沒有對應 `{來源檔案}` 單一段落可以逐條比對，驗證時改成確認：清單內容
  有沒有涵蓋所有規則 bullet、有沒有遺漏規則環繞的執行流程會牽涉到的
  章節。
- frontmatter 欄位是否都在支援清單內、`metadata.generated` 時間戳記是否
  只出現一次，也要一併檢查；`metadata.generated` 是否更新，要看這次
  生成的內容（時間戳記以外的部分）跟現有目標 `SKILL.md` 是否不同——不同
  才更新成本次時間，相同就保留原值，不能看到「跑過一次轉換」就直接
  覆寫。
- 比對過程要回報：對 `{來源檔案}` 做了哪些段落性質判斷（哪些歸類為規則
  本文、哪些歸類為範例／說明，尤其是沒有標題區分、靠語意判斷的部分）、
  改了本 Skill 哪幾條轉換規則、重新生成了幾輪，不能只回報「已確認吻合」
  的結論，讓使用者可以檢查比對是否真的逐條做過。

## 使用時機

想把一份給人看的規則文件（架構規範、程式碼慣例、流程規範，或任何其他
領域的規範）轉換成 AI 可以直接套用、逐條核對的可執行版 Skill 時，呼叫
本 Skill；規則正本異動後要讓對應 Skill 跟著更新時，也重新呼叫本 Skill
處理同一份來源。

## 自我檢查清單（每次轉換完成後逐條核對）

- [ ] 已先判斷 `{來源檔案}` 有沒有明確的規則／範例／說明標題結構；沒有
      的話，已逐段落／逐句靠語意判斷歸類，不確定的段落保守歸類為
      範例／說明。
- [ ] 目標 `SKILL.md` 只含規則本文，沒有搬入任何範例／說明段落的文字
      或程式碼。
- [ ] 目標 `SKILL.md` 的規則 bullet 逐條比對過來源，字句、括號例子、
      附帶子句都完整保留，沒有被精簡或省略。
- [ ] 沒有把範例／說明段落的推理文字接到規則 bullet 後面。
- [ ] 佔位符使用方式跟 `{來源檔案}` 本身的凡例一致：來源有定義佔位符
      就延用、沒有就照抄具體名稱，沒有臆測套用一套自訂佔位符規則。
- [ ] 若發現來源規則本文本身混進具體名稱、違反自己定義的凡例，已回頭
      修正 `{來源檔案}` 本文，不是在目標 `SKILL.md` 裡單方面代換。
- [ ] 程式碼區塊只保留原文放在規則本文段落的部分，範例／說明段落的
      程式碼一律沒有出現在目標 `SKILL.md` 裡。
- [ ] 目標 `SKILL.md` 全文（含 frontmatter）沒有出現對 `{來源檔案}` 或
      本 Skill 的檔案參照、連結或提及。
- [ ] 章節標題與編號跟 `{來源檔案}` 逐節一一對應。
- [ ] frontmatter 的 `name` 依規則來源所在資料夾名稱決定；`description`
      重新撰寫、不綁定專案名稱、不提 `{來源檔案}`；欄位都在 Claude Code
      支援清單內；`metadata.generated` 只出現一次。
- [ ] `metadata.generated` 有沒有更新過，已依「本次生成內容跟現有目標
      `SKILL.md` 是否不同」判斷：內容不同才改成本次時間，內容相同就
      保留原值，沒有單純因為跑過一次轉換就覆寫。
- [ ] 目標 `SKILL.md` 有「使用時機」「自我檢查清單」兩段內容；規則
      圍繞明確執行流程時，另外有對應的「執行清單」。
- [ ] 自我檢查清單顆粒度跟到每條規則 bullet，沒有把不同規則揉成一條
      打勾過關。
- [ ] 生成後已逐條比對來源與目標 `SKILL.md`，發現不吻合時已回頭調整
      本 Skill 的規則、重新生成整份目標 `SKILL.md`，重複到逐條吻合為止
      （不是直接手改目標 `SKILL.md`）。
- [ ] 回報時已說明：段落性質判斷結果、修改了本 Skill 哪幾條規則、重新
      生成了幾輪，而不是只回報「已確認吻合」。
